Part 1 — Frontend Philosophy & Architecture
1.1 Project Objective

The frontend of Restro Rasoi is not meant to be another CRUD dashboard.

It should feel like a premium Apple-quality application while remaining extremely fast and simple enough for someone with minimal technical knowledge (like your mother) to use daily.

The frontend has three primary objectives:

1. Speed

The application should allow recording a sale or expenditure in under 30 seconds, matching the business requirement described in the project flow.

That means:

minimal typing
large touch targets
keyboard shortcuts
dropdowns instead of text inputs
automatic calculations
minimal page switching

Every design decision should reduce the number of clicks required.

2. Simplicity

The user should never wonder

"What do I do next?"

Every page should have one primary action.

Examples

Dashboard

→ View business health

Sales

→ Record a Sale

Customers

→ Find a Customer

Menu

→ Manage Prices

Nothing more.

3. Reliability

The frontend is only responsible for

displaying information
collecting user input
validating basic inputs
improving UX

It must never become the source of truth.

The backend owns:

totals
calculations
profit
payment validation
business rules

If frontend and backend disagree,

Backend always wins.

1.5 Design Philosophy

The uploaded Design.md already establishes the visual language: a warm, Apple-inspired Liquid Glass interface with a fixed blurred kitchen background, translucent surfaces, and consistent design tokens.

We adopt the following rules:

Rule 1

Every page must feel like part of the same application.

Changing pages should never feel like switching websites.

Rule 2

The background never changes.

Only content changes.

Rule 3

Every floating surface uses the same glass recipe.

Only opacity changes.

Never invent new shadows.

Never invent new borders.

Rule 4

Spacing is consistent.

If cards have

24px

padding,

Every card has

24px

padding.

Rule 5

Animation is subtle.

Animation exists to communicate.

Not impress.

1.8 What the Frontend Owns

The frontend is responsible for:

Rendering UI
Responsive layouts
Client-side validation
User interactions
Loading states
Empty states
Animations
API calls
Caching
Form handling
Navigation
Accessibility
Optimistic UI (where appropriate)

It should not contain business rules that determine financial correctness.

1.9 What the Frontend Must Never Do

To keep the codebase maintainable, the following are prohibited unless there is a justified need:

Store server data in React Context.
Use multiple state management libraries.
Duplicate business calculations across components.
Call APIs directly from page components.
Hardcode colors, spacing, or typography instead of using design tokens.
Create one-off components that differ only slightly from existing reusable components.
Introduce UI libraries that overlap in functionality (for example, using both shadcn/ui and Material UI).
Trust values like grandTotal or netProfit received from user-modifiable inputs; always treat backend responses as authoritative.
1.10 Success Criteria

When this frontend is complete, it should meet the following standards:

Consistent: Every page follows the same layout, spacing, and interaction patterns.
Reusable: New features are built mostly by composing existing components.
Maintainable: A developer can locate any feature or component quickly.
Performant: Minimal bundle size, efficient rendering, and smooth interactions.
Accessible: Keyboard navigation, focus management, and readable contrast are built in from the start.
Production-ready: The project can grow from a family accounting tool into a larger business application without requiring a complete architectural rewrite.

3.24 Dead Code Policy

One of the project goals is to avoid unnecessary code.

Rules:

Remove unused components immediately.
Delete abandoned utility functions.
Avoid keeping "future" code commented out.
Don't create placeholder folders "just in case."
Remove unused imports before every commit.
If a dependency isn't used, uninstall it.

Treat the codebase like a workspace—keep it tidy.

3.25 Scalability Rules

When adding a new feature, the process should always be:

Create a new folder under features/.
Add only the files required:
components/
hooks/
services/
types/
schemas/ (if forms are involved)
Reuse existing shared components wherever possible.
Avoid modifying unrelated features unless necessary.

This keeps new features isolated and reduces the risk of regressions.

3.26 Folder Structure Checklist

Before introducing a new file, ask:

Does a similar file already exist?
Does this belong to a specific feature?
Can this be reused elsewhere?
Should it live in components, features, or utils?
Does it introduce unnecessary nesting?
Is the name descriptive and consistent?
           
If the answer isn't clear, rethink the placement before creating the file.                                                             

Part 4 — Next.js App Router Architecture

Objective: Design a scalable Next.js architecture that maximizes performance, keeps the codebase maintainable, and uses Server Components and Client Components intentionally—not randomly.

For Restro Rasoi, the frontend is built with Next.js App Router, while the backend remains a separate Express.js API as defined in the project flow. The frontend communicates with the backend over REST and does not directly access MongoDB.

4.1 Why Next.js?

Many developers use Next.js simply because it's popular.

We use it because it solves real problems.

We need

✓ Fast initial page load

✓ Better SEO (future-proof)

✓ Nested layouts

✓ Code splitting

✓ Image optimization

✓ Server Components

✓ Easy deployment on Vercel

✓ Excellent App Router

✓ Future scalability

4.2 Why App Router instead of Pages Router?

We will only use the App Router.

Reasons:

Better Layout System

Instead of

Every page recreates:

Sidebar

Navbar

Wrapper

Footer

we define them once.

Better Loading UI

Each route gets its own

loading.tsx

without writing custom logic.

Better Error Handling

Each route gets

error.tsx

instead of wrapping everything in try/catch.

Better Code Splitting

Every folder automatically becomes a route boundary.

Server Components

Biggest advantage.

Allows us to render data without sending unnecessary JavaScript.

Part 15 — Performance, Accessibility & Production Readiness

Objective: Ensure the application remains fast, accessible, and production-ready as the business grows. Performance and accessibility are architectural concerns and should be built into the project from the beginning rather than added later.

15.1 Performance Philosophy

Performance is measured by user experience, not benchmark scores.

The application should feel:

Instant
Responsive
Smooth
Predictable

Every optimization should have a measurable benefit.

15.2 Bundle Optimization

Guidelines:

Import only required modules.
Avoid large utility libraries when native APIs suffice.
Remove unused dependencies regularly.
Prefer tree-shakeable libraries.

Goal:

Keep the JavaScript bundle as small as practical.

15.3 Code Splitting

Lazy-load features that aren't immediately needed:

Charts
Drawers
Dialogs
Settings
Reports (future)

Critical UI should load first.

15.4 Image Optimization

Rules:

Use next/image for all static images.
Compress background assets.
Serve modern formats (WebP/AVIF when possible).
Define image dimensions to prevent layout shifts.

The Liquid Glass background should load once and remain cached.

15.5 Rendering Performance

Avoid unnecessary renders by:

Memoizing expensive components only when profiling justifies it.
Keeping state local.
Avoiding unnecessary Context updates.
Using stable query keys.

Do not overuse React.memo() or useMemo() prematurely.

15.6 React Query Performance

Configure queries appropriately:

Cache frequently used data.
Avoid duplicate requests.
Invalidate only affected queries.
Use background refetch where appropriate.

Do not disable caching unless absolutely necessary.

15.7 Large Lists

If data grows significantly:

Paginate first.
Virtualize only when pagination is insufficient.

Avoid rendering hundreds of rows simultaneously.

15.8 Accessibility

Every interactive element must support:

Keyboard navigation
Visible focus state
Screen readers
Sufficient color contrast
Touch-friendly sizing

Accessibility is a requirement, not an enhancement.

15.9 Keyboard Navigation

Ensure users can:

Navigate with Tab
Activate with Enter/Space
Close dialogs with Escape
Move through menus using Arrow keys where appropriate

Avoid keyboard traps.

15.10 Screen Readers

Every important control should have:

Accessible labels
Descriptive button text
Correct ARIA attributes when required

Do not rely solely on icons.

15.11 Responsive Design

Support:

Mobile
Tablet
Desktop

Layouts should adapt naturally without maintaining separate codebases.

15.12 Error Boundaries

Provide graceful fallbacks for unexpected React errors.

Display:

"Something went wrong."

with a retry or refresh option.

Prevent the entire application from crashing.

15.13 Monitoring & Logging

Future production deployments should support:

Error monitoring (e.g., Sentry)
Performance monitoring
API failure logging

Frontend logs should help debugging without exposing sensitive information.

15.14 Lighthouse Goals

Target:

Performance ≥ 90
Accessibility ≥ 95
Best Practices ≥ 95
SEO ≥ 90 (future public pages)

These are goals, not absolute requirements.

Throughout the project, follow these principles:
